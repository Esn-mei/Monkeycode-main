# 文件系统沙箱兜底技术方案

## 架构概览

以 `WorkspaceGuard` 作为所有内置文件工具共用的文件系统边界。每次访问先取得工作区根目录的规范真实路径，再将用户输入路径归一化并解析符号链接，最后以路径组件关系判断目标是否仍位于根目录中。权限管理在调用工具前使用同一边界预检查；文件工具在真正 I/O 前再次执行边界检查，形成防御纵深。

该方案覆盖内置的读取、写入、编辑、文件发现和代码搜索。worktree 子 Agent 已将自己的 worktree 注入工具上下文，因此不需要新增另一套根目录模型。

## 模块划分

| 模块 | 职责 |
| --- | --- |
| 工作区路径守卫 | 规范化根目录和候选路径，解析符号链接，确认路径组件仍在根目录下，输出受信任的绝对路径或统一错误。 |
| 文件工具 | 在实际读取、写入、编辑前使用受信任路径；写入同时验证目标与父目录，拒绝目录或链接逃逸。 |
| 搜索/发现工具 | 枚举时逐项通过路径守卫，仅处理项目根目录内的真实文件。 |
| 权限管理 | 将路径守卫作为不可绕过的硬检查，在规则匹配和用户确认之前拒绝逃逸。 |
| 测试 | 覆盖各工具、权限模式、worktree 与跨平台可用的符号链接场景。 |

## 核心接口与数据流

```text
工具参数 path
   -> 工作区路径守卫
      -> 解析 project root 的真实路径
      -> 拼接/规范化候选路径
      -> 解析候选路径及其已有父路径中的符号链接
      -> 路径组件前缀判断
   -> 受信任目标路径 / WorkspaceError
   -> 文件 I/O 或结构化 path_outside_workspace 结果
```

路径守卫维持两个面向行为的能力：

1. `resolve_existing` 语义：用于读取、编辑、搜索以及已存在目标，解析完整符号链接后确认边界。
2. `resolve_writable` 语义：用于创建/覆盖。它必须分别验证目标的真实路径（若目标存在）及最近存在父目录的真实路径；不能因目标尚不存在而跳过链接检查。

两类能力均只返回已通过工作区包含关系检查的路径。包含关系使用 `relative_to` 等路径组件级比较，不能使用字符串 `startswith`。

## 关键技术决策

### 使用真实路径而不是字符串比较

理由：`..`、大小写、绝对路径以及符号链接均可能使文本前缀与实际位置不一致。先解析再按路径组件比较可跨平台覆盖这些情况。

### 保留“授权前检查 + I/O 前检查”

理由：权限层防止允许规则放行非法路径；工具层确保未来新增调用方或权限接入变化时仍不会直接 I/O 到项目外。两层共享同一守卫，不复制判定逻辑。

### 写入检查以父路径为核心

理由：新文件没有完整的可解析实体，但其父目录决定最终落点；已有目标还可能本身是符号链接。因此写入必须同时覆盖二者。

### worktree 以 ToolContext 根目录天然隔离

理由：worktree 子 Agent 的文件工具已使用其工作目录作为 `workspace_root`。路径守卫只信任上下文根目录，即可将主项目、其他 worktree 和系统目录同等视为项目外。

### 不将 Shell 纳入本方案

理由：Shell 可通过解释器、重定向和子进程间接访问任意路径，可靠限制需要独立的 OS 受限进程或容器后端；对文件工具做表面过滤不能构成 Shell 沙箱。

## 风险与回退

| 风险 | 缓解方式 | 回退 |
| --- | --- | --- |
| 非特权 Windows 环境无法创建符号链接 | 测试在无法创建链接时按现有测试约定跳过，仅保留正常路径和绝对路径测试。 | 不降低运行时代码检查。 |
| 解析后与实际打开间存在并发替换竞态 | 记录为非本次范围；不将文件工具安全边界描述为完整 OS 级隔离。 | 后续独立引入平台受限句柄/容器后端。 |
| 收紧检查影响合法项目内路径 | 为项目内相对/绝对路径、worktree 和已有合法链接加入回归测试。 | 若出现兼容问题，仅调整对项目内真实路径的判定，不允许放宽项目外访问。 |
| 新工具绕过守卫 | 把守卫作为文件工具实现与权限硬检查的统一入口，并在代码审查中检查所有 I/O 工具。 | 新工具上线前补接入与测试。 |
